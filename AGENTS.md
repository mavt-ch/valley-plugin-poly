# Poly plugin

- Poly (25 Nov: Study renamed to Poly and merged with Zürich 3D, on request) is ETH and UZH in Valley: the eLink shuttle, the Menu plan and the Campus map (25 Nov: Zürich 3D became the campus map's 3D view, on request: "make it more like maps"). One left-sidebar panel `poly.panel`, an Icon Rail entry (never declare `rail: "tab"`), icon `icon.svg`: the Zürich Polybahn, a funicular car with three window panes on an inclined track, stroke 1.75 on the 24 grid (keep the panes filled and at least 1 unit clear of the outline so it reads at 15px). The panel is laid out like Map's sidebar (25 Nov): row 1 the shared `panel-header` with only the shown feature's name and the host `plugin-open-page` button, which opens the shown feature's page; row 2 the feature tabs (`.poly-tabs` / `.poly-tab`, a copy of Map's `.map-tabs` / `.map-tab`: 38px row, 30×26 icon buttons, 16px glyphs, `--accent-tint-bg` when active, the name as tooltip, arrow keys/Home/End move), eLink (a bus, first: 25 Nov, "I want all the connection eLink at the very beginning"), Menu plan (fork and knife), then Campus map (26 Nov: ETH's main building as seen from the Polyterrasse, long low wings with windows, a wider centre with three arched windows, door and flagpole; the same glyph as the menu plan's ETH tag, `CAMPUS_ICONS.eth`), then ETH News (27 Nov, on request: its own icon, a folded newspaper, `NEWS_ICON`). The user orders the tabs (26 Nov, on request: "make that I can reorder the icons"): dragging a tab sideways (pointer events with a 4px threshold, the tab follows the pointer, the others make room, saved on release; a drag is never a click) or Option/Alt + arrow on the focused tab, saved in the hidden `tabOrder` setting (`tabOrderOf` keeps every mode once and appends missing ones). The shown tab is saved in the hidden `mode` setting (`elink` | `menu` | `campus` | `news`, default `menu`; 2.0.0's `city` is read as `campus` and rewritten on the first panel render, so the enum keeps `city`). Never put a mode switch back into row 1. One page `poly.page`, a fully custom main-workspace view: instance `campus` or `campus-<id>` (`isCampusInstance`, which also takes 2.0.0's `city` / `city-<id>`) is the campus map, instance `elink` (`isElinkInstance`) the eLink timetable, any other instance the menu plan (25 Nov: "not a link but completely custom": dish cards with pictures, never an embedded or linked website). Both features are built from `src/views.tsx`; the campus map's code lives in `src/campus/` and `src/backend/campus.ts` (strings under `campusMap.`; `campus.*` keys belong to the menu plan's campus tags), the 3D model's in `src/city/` and `src/backend/city.ts` (strings under `city.`), all in the same five catalogs. Later features join these surfaces; they never move code into Valley core.
- The page's first bar keeps the host's reservations: `--plugin-navigation-offset` at the start (back/forward) and `--plugin-actions-offset` at the end (host menu).
- Menu data comes only from ETH's Cookpit service (`idapps.ethz.ch`, client id `ethz-wcms`, the one ETH's gastronomy page sends), the ZFV's food2050 pages (`app.food2050.ch`) and food2050's picture bucket (`storage.googleapis.com/dish-images-prod/`). `permissions.network.hosts` holds exactly these three. Never invent prices, opening hours or dishes a source does not supply. UZH prices and pictures come only from each dish's own page, read when its card is on screen.
- Host limits the backend must respect: `maxResponseBytes` at most 4 MiB (a larger ask is refused before any request; 25 Nov, every request failed with 6 MB). Cookpit answers 406 to `Accept: image/*` alone; picture requests accept `*/*` too. The tests' mock enforces both.
- ETH facilities are sorted by postcode, ETH's own rule (`ethZone`): Hönggerberg 8093, 8049, 8053 (`HOENGGERBERG_POSTCODES`), Oerlikon 8050, Basel 4xxx, Zentrum the rest; the tags ETH = Zentrum and Höngg = Hönggerberg, Oerlikon and Basel are not shown. Never a hard-coded facility list. UZH outlets come from the organisation page `universitat-zurich`; never a hard-coded outlet list.
- food2050 has no public API: `src/model.ts` reads the payload streamed in `self.__next_f.push([1,"…"])` scripts, takes the component properties that start with `{"outlet":` or `{"organisation":` and resolves the payload's `"$<id>:props:…"` references. When food2050 changes its pages, fix the parser and its fixtures in `tests/fixtures.ts`.
- Lunch and dinner are told apart by the meal's start time for ETH (from 15:00 is dinner) and by the category name or slug for UZH (`abend`, `dinner`, `evening`).
- Network requests run only in the backend (`src/backend/index.ts`), at most two at once, with a 30-minute memory cache for menus and 12 hours for the outlet lists and each outlet's page; `fresh: true` (Refresh) asks past it. The place list reads every UZH outlet's week as soon as the outlet list is known (25 Nov decision: complete counts and tags over lazy counts; 26 outlets, 2–3 requests each the first time, 1–2 once the outlet pages are cached) with `background: true`, which queues those reads behind the open page's reads and pictures.

- 3D city model (merged from the local `zurich3d` package, the campus map's 3D view since 25 Nov): the city model ships in the package (26 Nov, on request: "put the whole 3d thing into the poly folder" so the repository works as uploaded to GitHub): `runtime/assets/model/` is its only copy in the repository (a second copy elsewhere would be in GitHub's zipball twice), written by `npm run update-model` and carried into every new `runtime/` by `build.mjs` (APFS clone). It must load through a realm whose Poly package is a symbolic link to the repository (26 Nov, on request: "even with an alias"): the host's storage grants never traverse a link (a security boundary; never weaken it in core, never ask for `external` for this), but the plugin's own assets follow one, so each model file is one classic script `<file>.js` that calls `valleyPolyModel("<file>","<base64>")` (`tooling/modelAssets.mjs` writes and reads them, `src/city/modelAssets.ts` loads them through `api.assets.url` into the frame's own document, script-src `'self'`; the frame CSP forbids `fetch`, so never fetch, and never use another document or WebAssembly for this). Never read the packaged model through storage grants on `plugins/packages/…` again. Only a model in the realm's `.valley/plugins/data/poly/model/` (`npm run update-model -- --realm <realm>`, plain files) goes through the backend: one metadata grant for it in `config.json`, beside Polybox's `plugins/data/poly/polybox` and nothing else (a test pins both), bytes mode (`model.read`, 2 MiB chunks, a `largeDataOperations` entry); it wins over the packaged one, and a folder the host refuses (absent, or behind a link) counts as none, so the packaged model is used. Load failures show `city.model.errorText` in plain words, never the host's error text (logged with `console.warn`). The package must stay under the installers' limits: 32 MiB zip download (`npm run check` allows 28 MiB), 2,000 files, 16 MiB per file; the tile format exists to fit them (version 2: 5 cm quantization, per-axis zigzag deltas in byte planes, vertices shared within a building only, varint index codes, about 26 MB of model files for the city, 34 MB packed as base64 scripts and about 24 MiB in `npm run check`'s zip estimate, since deflate takes base64 back to about the binary size; never add a decoder dependency or WebAssembly for it). Change the tile layout only in `tooling/tileFormat.mjs` and `src/city/tileFormat.ts` together, with a version bump and the round-trip test (the format id stays `zurich3d-tiles`); the decoder keeps reading version 1, which older realm-installed models use. A loaded tile keeps the decoder's 16-bit positions (26 Nov): `tileGeometry` in `src/city/scene.ts` pads them to four per vertex in an interleaved attribute and places them with a matrix (origin, step, LV95 → scene axes), colours are RGBA bytes; both strides stay multiples of 4 bytes because ANGLE on Metal copies other strides, and nothing keeps a per-vertex float copy (height colours are computed per building while painting). Highlight and area meshes share the tile's position attribute and must carry the tile's matrix; LV95 from a vertex is `origin + value × step`. `tests/city-tileGeometry.test.ts` pins placement and raycast hits against the float geometry. Base64 is decoded only by `src/base64.ts`. Rust/WebAssembly was weighed for the decoder and the backend and not used (26 Nov): the JIT decoder takes about 0.3 ms per tile and the backend waits on the network. The view renders in the surface document: canvas, `requestAnimationFrame`, observers and listeners come from the container's `ownerDocument`/`defaultView`; render on demand, never a continuous loop while idle. The ground is an approximation from building base heights, labelled as such. Commands of kind `read` must not write settings (`valley-plugin check` refuses it). Setting schemas in `config.json` need an explicit `type` (`"union"` with `anyOf`): the host refuses the whole package otherwise, while `npm run check` passes. A custom `settingsView` would replace every schema field, so Poly has none; the model's update command (`npm run update-model`, then `npm run build`) is documented in the README and shown only while a package was built without its model.
