# Poly plugin

- Poly (25 Nov: Study renamed to Poly and merged with Zürich 3D, on request) is ETH and UZH in Valley: the eLink shuttle, the Menu plan and the Campus map (25 Nov: Zürich 3D became the campus map's 3D view, on request: "make it more like maps"). One left-sidebar panel `poly.panel`, an Icon Rail entry (never declare `rail: "tab"`), icon `icon.svg`: the Zürich Polybahn, a funicular car with three window panes on an inclined track, stroke 1.75 on the 24 grid (keep the panes filled and at least 1 unit clear of the outline so it reads at 15px). The panel is laid out like Map's sidebar (25 Nov): row 1 the shared `panel-header` with only the shown feature's name and the host `plugin-open-page` button, which opens the shown feature's page; row 2 the feature tabs (`.poly-tabs` / `.poly-tab`, a copy of Map's `.map-tabs` / `.map-tab`: 38px row, 30×26 icon buttons, 16px glyphs, `--accent-tint-bg` when active, the name as tooltip, arrow keys/Home/End move), eLink (a bus, first: 25 Nov, "I want all the connection eLink at the very beginning"), Menu plan (fork and knife), then Campus map (location pin), saved in the hidden `mode` setting (`elink` | `menu` | `campus`, default `menu`; 2.0.0's `city` is read as `campus` and rewritten on the first panel render, so the enum keeps `city`). Never put a mode switch back into row 1. One page `poly.page`, a fully custom main-workspace view: instance `campus` or `campus-<id>` (`isCampusInstance`, which also takes 2.0.0's `city` / `city-<id>`) is the campus map, instance `elink` (`isElinkInstance`) the eLink timetable, any other instance the menu plan (25 Nov: "not a link but completely custom": dish cards with pictures, never an embedded or linked website). Both features are built from `src/views.tsx`; the campus map's code lives in `src/campus/` and `src/backend/campus.ts` (strings under `campusMap.`; `campus.*` keys belong to the menu plan's campus tags), the 3D model's in `src/city/` and `src/backend/city.ts` (strings under `city.`), all in the same five catalogs. Later features join these surfaces; they never move code into Valley core.
- The page's first bar keeps the host's reservations: `--plugin-navigation-offset` at the start (back/forward) and `--plugin-actions-offset` at the end (host menu).
- Menu data comes only from ETH's Cookpit service (`idapps.ethz.ch`, client id `ethz-wcms`, the one ETH's gastronomy page sends), the ZFV's food2050 pages (`app.food2050.ch`) and food2050's picture bucket (`storage.googleapis.com/dish-images-prod/`). `permissions.network.hosts` holds exactly these three. Never invent prices, opening hours or dishes a source does not supply. UZH prices and pictures come only from each dish's own page, read when its card is on screen.
- Host limits the backend must respect: `maxResponseBytes` at most 4 MiB (a larger ask is refused before any request; 25 Nov, every request failed with 6 MB). Cookpit answers 406 to `Accept: image/*` alone; picture requests accept `*/*` too. The tests' mock enforces both.
- ETH facilities are sorted by postcode, ETH's own rule (`ethZone`): Hönggerberg 8093, 8049, 8053 (`HOENGGERBERG_POSTCODES`), Oerlikon 8050, Basel 4xxx, Zentrum the rest; the tags ETH = Zentrum and Höngg = Hönggerberg, Oerlikon and Basel are not shown. Never a hard-coded facility list. UZH outlets come from the organisation page `universitat-zurich`; never a hard-coded outlet list.
- food2050 has no public API: `src/model.ts` reads the payload streamed in `self.__next_f.push([1,"…"])` scripts, takes the component properties that start with `{"outlet":` or `{"organisation":` and resolves the payload's `"$<id>:props:…"` references. When food2050 changes its pages, fix the parser and its fixtures in `tests/fixtures.ts`.
- Lunch and dinner are told apart by the meal's start time for ETH (from 15:00 is dinner) and by the category name or slug for UZH (`abend`, `dinner`, `evening`).
- Network requests run only in the backend (`src/backend/index.ts`), at most two at once, with a 30-minute memory cache for menus and 12 hours for the outlet lists and each outlet's page; `fresh: true` (Refresh) asks past it. The place list reads every UZH outlet's week as soon as the outlet list is known (25 Nov decision: complete counts and tags over lazy counts; 26 outlets, 2–3 requests each the first time, 1–2 once the outlet pages are cached) with `background: true`, which queues those reads behind the open page's reads and pictures.
- Menu plan design (25 Nov, on request): below the shared header and tab rows the sidebar is exactly three 38px rows, then the place list, never dishes (25 Nov: Lunch | Dinner moved down to the day row to make room); first the tags Favorites, ETH, Höngg, UZH drawn like To-Do's smart-list chips (icon tinted in the tag colour, label, count, filled when active; single choice like To-Do, saved in `campus`) with Contacts' 6px tag corners (25 Nov); a campus tag shows only while its campus has a place serving the meal that day, Favorites (yellow star, first) while any place is starred, listing the starred places of every campus (ETH ones prefixed ETH/Höngg). Every place row and the place page's bar carry a star (outline; filled `--color-yellow` when a favourite), saved as location ids in `favorites`. Campus icons are line drawings of the buildings (25 Nov): ETH the main building from the Polyterrasse (flat centre block with columns, flagpole, wings), UZH the main building's domed tower between hipped wings; keep them sparse enough to read at 15px; then the week row (26 Nov, on request): ‹, Monday to Sunday of the shown week as seven cells (short weekday above the date), today in `--accent-color`, the chosen day filled with `--accent-tint-bg`, ›; the chevrons move one week (same weekday), ‹ is disabled on this week and never lands before today; then the meal row: Lunch | Dinner, then at the end the three price-group icons (graduation cap Students, briefcase Staff, person Guests), a divider and the food filter (a salad bowl with a leaf, 26 Nov: "make a food filter"; never a funnel or sliders). A place row shows name, menu count after filters, location and, only where the source gives opening hours, Open now/Closed with the hours. Place rows are drawn like Email's message list (25 Nov: full width, no padding or margin around the list, square, a 1px `--border-light` line under each row) and the row of the place whose page is the focused tab (`getState().activePluginTab`, followed through `api.subscribe`) carries Contacts' selection: `--accent-tint-bg` with the name in `--accent-color`. A click opens `study.page` with `instanceId` `place:<location id>` (⌘/middle click a new tab); without an instance the page shows the chosen campus. The page's first bar names only the place (the campus on the overview), centred, with Refresh at the end (25 Nov: "since this is already on the left sidebar only write down the mensa name"): never repeat the sidebar's day, Lunch | Dinner or filter controls on the page, and do not repeat the name as a heading in the page body. A place's facts (location, opening state with hours, serving time, menu count) are a second fixed bar under it (25 Nov): `var(--app-bar-height)`, centred, one line that never wraps or scrolls with the cards (the location truncates first); only the cards below scroll. Day and meal are shared by both surfaces through the hidden `day` setting (a day before this week's Monday falls back to today; earlier days of this week stay). Filters are the `onlyVegetarian`, `onlyVegan`, `onlyGlutenFree`, `onlyLactoseFree` switches, edited from the funnel menu (Vegetarian leaf, Vegan sprout | separator | Gluten-free crossed-out wheat, Lactose-free crossed-out milk carton; every item carries its icon) and Settings → Study alike; whose prices the cards show is the three group icons before the funnel (26 Nov, replacing 25 Nov's cash-button menu): a click shows only that group's price, a click on the active icon shows all prices again, saved in `prices` (default `all`; a new key, so 1.1.x's stale `price` never comes back) and in Settings → Study; a group shows only its price via `priceFor` (its own, else a shared price covering it), never a guess when the source has none for that group. Gluten-free and lactose-free need declared allergens without a gluten cereal / milk (`gluten === false`, `lactose === false`); never call a dish without declared allergens gluten- or lactose-free. A dish card has one compact form and never opens or expands (25 Nov: "only one tile of menu and not separate, I like the smaller view"): line with every price on one line students → guests (`pricesInOrder`, "CHF 7.90 / 10.90 / 13.90", the groups named in the tooltip; when the line's name does not fit, the prices drop to their own row rather than cutting it), name, description, then the allergens directly above the tags.
- Fixtures are invented (no staff names or real manager data from Cookpit's facility records). The eLink fixtures (`tests/elink-fixtures.ts`) are trimmed transport.opendata.ch stationboards: public timetable data with no personal data.
- eLink (25 Nov, on request): line E of the operator VBG only, from transport.opendata.ch's public stationboards (25 Nov, on request: use open transport data when it has eLink; it does, so search.ch was dropped; never ETH's `eduapp.ethz.ch` gateway, which needs a login). Keep the VBG filter (`isElink`): the service also returns an unrelated VBZ line E at ETH/Universitätsspital. A run's direction comes from the board's stop and the last stop of its `passList` (`directionOf`: Universitätsspital → Hönggerberg, Hönggerberg → Universitätsspital, Bahnhofplatz/HB → Hönggerberg, Hönggerberg → Bahnhofplatz/HB or Bahnhofquai/HB), never from a hard-coded timetable; the downloaded CSV/JSON are not shipped. Requests ask only buses and the read `fields[]`; `limit` is at most 420 (a larger one is refused), so each stop's day is read page by page from 00:00, the next page starting at the last page's last minute, until a page is short or reaches the next day (at most five; Hönggerberg takes two), two requests at a time, cached two minutes for today and 30 minutes otherwise. Delays come only from `stop.delay`; the v1 API reports no cancellations, so none are shown; never invent runs, and say *No eLink on weekends.* for an empty Saturday or Sunday. Design (25 Nov, on request, after a departure-board screenshot: "not the boxes not the name but the train number and how many minutes but also write the time"): rows of line badge (white, black E), destination, time and minutes ("6'", under an hour, today only) under a plain direction heading with first/last run; no cards or tables. The day is the hidden `elinkDate` setting shared by the sidebar and the page (a past day is today). Code: `src/elink/`, `src/backend/elink.ts`; strings under `elink.`.

- Campus map (25 Nov): ETH's buildings only, never invented data. The building list is the one shipped file (`src/campus/buildings.json`, generated by `tooling/buildings.mjs` from ETH's CSV: trimmed fields, CLG's link fixed from BHA's, LUI's split street, "Zuerich"/"Zürch"; never hand-edit it). Campus groups follow ETH's site plans exactly (Zentrum and Hönggerberg code lists in the script, everything else Other sites, even at 8093 such as HIG and HPG); the site-plan codes FHK, STE, STS, HPQ and HRZ are not in ETH's building list and so not shown. Outlines, floors and rooms are never package or realm content: the backend reads them live from ETH's public ArcGIS services on `arcgis-prd-web.ethz.ch` (Facilities 5, Levels 2, Units 1; `f=geojson`, `orderByFields=OBJECTID`, pages of 2000 until `exceededTransferLimit` is gone, 12-hour memory cache, a floor id must match `LEVEL_ID` before it goes into a `where`). The base map is blank (25 Nov, on request: "a more blank one instead of the fully thing one"): Esri's World Light / Dark Gray Base from `server.arcgisonline.com` (keyless, OpenStreetMap data), the dark set in the dark appearance (the theme is part of the protocol address, so a theme change reads the other set), through the backend (`campus.tile` with `dark`, bytes mode, a `largeDataOperations` entry), six at a time; source `maxzoom` 16, MapLibre enlarges above it. Not CARTO (its blank tiles answer "API key required"), not OpenStreetMap's standard tiles (full of symbols), never an inverted light set. The 2D engine is MapLibre (`src/campus/mapIsland.ts`), bundled by `build.mjs` into `runtime/assets/campus-map.js` and loaded into the page's own document like Map's island (MapLibre uses the realm it runs in); data handed to it is cloned in its realm (`structuredClone`, tile bytes copied) because MapLibre's worker refuses objects from the plugin's frame. No glyph server: labels are images drawn on `styleimagemissing`. MapLibre's own zoom and attribution controls are off. The 2D map turns like the 3D view (26 Nov, on request: "turn the orientation by clicking on command and then turn around"): ⌘-drag, handed to MapLibre as the same press with Control (`commandAsControl` in `src/campus/mapGestures.ts`, a capture listener on the map container), so MapLibre's own rotate handler turns it, snaps to north within 7° and suppresses the click; a right-button drag and two-finger touch rotate too. It never tilts (`pitchWithRotate: false`), the bearing is part of the session camera, and framing (`fitBounds`) keeps the current bearing; the page draws round Valley zoom buttons and a "Map © Esri, HERE, Garmin, © OpenStreetMap contributors · Buildings © ETH Zürich" line. Selection (`building`), floor (`level`, must belong to the building) and view (`campusView`, `map` | `3d`) are hidden settings shared by sidebar and page; a selection from the sidebar frames the building and brings the campus page to the front, a click on the map or the model only selects. The floor strip lives on the page (top floor first), not in the sidebar. The selected building is pinned to the bottom of the sidebar below the scrolling list as a plain strip (25 Nov, on request: "make the box not as box no left-right border margin and padding no buttons only say HG / adress / adress 2 / link … height of 37px*3"): exactly `var(--app-bar-height) * 2 - 2px` (74px; on request: "if 37*2px also fit then do that and also add the close icon") tall with a hairline above, no border, margin or card, four lines at line-height 1.25: code, address, campus · floors, ETH page link, and only a × at the top right that clears the selection (no Search, 3D or Map); text keeps the list rows' 10px inset. 2D/3D is switched only by the page's round control. The campus sidebar always lists the same four groups in this order, in 2D and 3D (25 Nov): ETH Zentrum, ETH Hönggerberg, Other sites, Zürich (the landmarks of `src/city/geo.ts` `PLACES`, filtered by the search; a click flies the 2D map (`showPlace`, zoom from the viewing distance) or the 3D camera); never a separate 3D section in the sidebar. In 3D only, the page's round controls add colour by height (`colorMode`) and the ground switch (`showGround`) after the 2D button; the clicked LoD2 building and the model facts are the right sidebar's Properties tab `poly.city3d` ("3D city", `METADATA_PANEL_SEGMENT_V1`, campus tabs only, a one-line note while the page shows 2D); the clicked building's facts (EGID, height, ground, roof, LV95 position, triangles) appear only there, never as a card on the 3D page (26 Nov, on request: "show this in the right-sidebar property instead on the content page"); its notes only say where the data comes from (Stadt Zürich model with its Source link, then the map and ETH credit), never a command such as `npm run update-model` (26 Nov). Before it, the Properties tab `poly.building` ("Building", 26 Nov, on request) shows the selected ETH building in 2D and 3D (code, address, campus, floors, the shown floor, ETH building page) and, once a room is picked or clicked, a Room section (name, floor, type, use, kind with its legend colour); without a selection a one-line hint. On the campus page the room legend and the credit line share one bottom row (`.poly-map-foot`, 26 Nov: they overlapped): side by side when they fit, the legend wrapping above the credit when not. The campus page's bar shows only the building's name and address: no Map | 3D switch and no home button there (25 Nov, on request: "remove the Map 3D and home icon in the header"). The page's controls are Map's round buttons (`.poly-round-btn`, a copy of `.map-round-btn`, stacked like `.map-overlay-controls`): only +, − and the 2D/3D switch (25 Nov, on request: "similar to the map thing in maps and only use + and minus and then also add the 3d and 2d thing"), in both views; + and − zoom the 2D map one level or move the 3D camera 40 % nearer/farther. MapLibre's own controls stay off. Room search (25 Nov) is one bounded Units query per search (`campus.searchRooms`, 40 rows, by `NAME`): `parseRoomQuery` turns `HG F7` / `F7` (selected building) / `HG F` into `NAME LIKE 'HG F 7%'` and `HG Hörsaal` into a building-scoped `UPPER(USE_TYPE)`/`UPPER(RaumTyp)` match (umlauts as ASCII, as ETH writes them); only letters, digits, dots and spaces reach the SQL (`roomWhere` refuses anything else) and the building must be in the shipped list. The picked room (searched or clicked) is hatched ("schraffiert", 25 Nov) in the accent colour with its number inside (`roomLabel`: "F 7", without the building code): in 2D a `fill-pattern` image drawn on `styleimagemissing` plus a large label that ignores collisions (the room's small number gives way), in 3D a world-UV stripe texture over a light slab plus a camera-facing sprite; both textures come from the view's own document and are disposed with the floor. In 3D a selected building highlights every LoD2 building that belongs to it (25 Nov: every ETH building in the model must highlight and be looked into like HG; `src/city/match.ts`): at least `MIN_SHARE` 50 % of its footprint (ground surfaces, else roofs, from the tile's triangles) inside ETH's outline, or covering at least `MIN_COVER` 30 % of the outline (the ETH building is part of a bigger LoD2 building); never the bounding-box centre (HIL, KO2, HPV and others matched nothing or neighbours). After changing the rule or the model run `node tooling/check-3d-match.mjs` (packaged model; `--realm <realm>` for a realm-installed one) (25 Nov: 164 in the model, 160 matched; HDB, LGA, Y35, Y59 have no footprint there). With a floor the tile's draw groups hide those buildings, a translucent shell takes their place and the rooms are one flat vertex-coloured mesh at base + `floorElevations` (storeys stacked from order 0 by `HEIGHT_RELATIVE`); without a model building the base is the ground at the outline, never no floor. The floor also marks the stencil before the ground is drawn (`GROUND_STENCIL`, on every ground material), so a floor below the approximate ground (basements, slopes) shows through the map; a clicked building's solid highlight hides while its floor is shown. A 3D click selects the ETH building at the clicked spot, then at the LoD2 footprint centre. A selection writes its settings asynchronously, so the stages hear of `focus` only once the building it was bumped for (`focusOn`) is shown, and the 3D view flies once per `focus` (25 Nov: the first pick flew to the building shown before). Everything in 3D still renders on demand. The 3D ground carries the same base map (25 Nov, on request: "for the 3d data and under it is the map"; `src/city/groundMap.ts`): each Web Mercator tile is a 8 × 8 grid projected to LV95 (`wgs84ToLv95`) and lifted onto `groundHeight` 0.6 m below the building bases, its texture the tile's own pixels; one zoom at a time from the camera distance (`groundZoom`: 16 below 450 m, 15, 14, 13 beyond 3.6 km), at most 64 wanted, four loading, 96 kept; `update` runs from `updateTiles` and asks for a frame only when what it shows changed (never an idle loop); with the map, the plain ground mesh stays hidden and the Ground switch shows or hides the map.
- 3D city model (merged from the local `zurich3d` package, the campus map's 3D view since 25 Nov): the city model ships in the package (26 Nov, on request: "put the whole 3d thing into the poly folder" so the repository works as uploaded to GitHub): `runtime/assets/model/` is its only copy in the repository (a second copy elsewhere would be in GitHub's zipball twice), written by `npm run update-model` and carried into every new `runtime/` by `build.mjs` (APFS clone). It must load through a realm whose Poly package is a symbolic link to the repository (26 Nov, on request: "even with an alias"): the host's storage grants never traverse a link (a security boundary; never weaken it in core, never ask for `external` for this), but the plugin's own assets follow one, so each model file is one classic script `<file>.js` that calls `valleyPolyModel("<file>","<base64>")` (`tooling/modelAssets.mjs` writes and reads them, `src/city/modelAssets.ts` loads them through `api.assets.url` into the frame's own document, script-src `'self'`; the frame CSP forbids `fetch`, so never fetch, and never use another document or WebAssembly for this). Never read the packaged model through storage grants on `plugins/packages/…` again. Only a model in the realm's `.valley/plugins/data/poly/model/` (`npm run update-model -- --realm <realm>`, plain files) goes through the backend: one metadata read grant in `config.json` (a test pins it), bytes mode (`model.read`, 2 MiB chunks, a `largeDataOperations` entry); it wins over the packaged one, and a folder the host refuses (absent, or behind a link) counts as none, so the packaged model is used. Load failures show `city.model.errorText` in plain words, never the host's error text (logged with `console.warn`). The package must stay under the installers' limits: 32 MiB zip download (`npm run check` allows 28 MiB), 2,000 files, 16 MiB per file; the tile format exists to fit them (version 2: 5 cm quantization, per-axis zigzag deltas in byte planes, vertices shared within a building only, varint index codes, about 26 MB of model files for the city, 34 MB packed as base64 scripts and about 24 MiB in `npm run check`'s zip estimate, since deflate takes base64 back to about the binary size; never add a decoder dependency or WebAssembly for it). Change the tile layout only in `tooling/tileFormat.mjs` and `src/city/tileFormat.ts` together, with a version bump and the round-trip test (the format id stays `zurich3d-tiles`); the decoder keeps reading version 1, which older realm-installed models use. The view renders in the surface document: canvas, `requestAnimationFrame`, observers and listeners come from the container's `ownerDocument`/`defaultView`; render on demand, never a continuous loop while idle. The ground is an approximation from building base heights, labelled as such. Commands of kind `read` must not write settings (`valley-plugin check` refuses it). Setting schemas in `config.json` need an explicit `type` (`"union"` with `anyOf`): the host refuses the whole package otherwise, while `npm run check` passes. A custom `settingsView` would replace every schema field, so Poly has none; the model's update command (`npm run update-model`, then `npm run build`) is documented in the README and shown only while a package was built without its model.
